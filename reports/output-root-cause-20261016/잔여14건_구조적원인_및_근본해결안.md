### 20번 Omios Biologics — 전문 과업과 공급 근거의 간극

N018의 스파이더코어·에이아이클라우드·엘앤피솔루션은 유전자 치료제, 항체·저분자, 화합물/단백질-리간드 등의 기능을 설명합니다. 수요 업무는 **용해성 바이러스 후보 설계**입니다. 같은 신약개발 Task 안에서도 대상 물질과 설계·평가 기능이 다릅니다. 세 카드가 생략된 직접 사실은 확인되지만, 모델이 생략 사유를 반환하지 않아 각 생략의 확정 사유는 알 수 없습니다. 원천 설명을 대조하면 바이러스 설계 지원 근거의 공백이 보입니다.

N019의 지니너스 IntelliMed는 악성세포 분류와 단일세포·공간 오믹스 기반 타깃 발굴을 설명합니다. 해당 카드에 대한 audit는 수요 업무의 **바이러스·숙주 상호작용 분석**을 뒷받침하지 못한다고 명시했습니다. 이는 단순한 문장 길이나 필드 표시 오류가 아닙니다.

근본 해결은 과업을 물질/모달리티·분석 기능·입력/출력으로 분해하고, 해당 기능의 공급 근거를 다시 탐색·검증하는 것입니다. 현재 워크북의 Task 연결 후보 밖도 근거 기반으로 검색할 수 있어야 합니다. **현재 후보의 근거 부족이 전체 공급기업 풀이나 시장에 업체가 없다는 뜻은 아닙니다.** 바이러스 관련 전문기능이 확인되지 않은 업체를 일반 플랫폼이라는 이유로 전문 공급기업으로 확정해서는 안 됩니다.

### 23번 레디큐어 — 업무 정의가 공급기능보다 넓고, 범용 도구와 의료 분석이 섞임

J063은 치료 설정값·장비 제어 데이터·모델 평가 결과를 함께 분석하는 업무입니다. 첫 후보 3개가 생략된 뒤 예비 후보도 검토했으므로, 이전의 ‘최초 3곳만 보고 종료’ 문제는 이번 실행에서 이미 보완됐습니다. 그래도 6곳 중 5곳이 생략됐고, 마키나락스 Runway만 카드가 생성됐습니다.

Runway 원천에는 **범용 MLOps와 실험 이력 비교·재현**이 실제로 있습니다. audit도 기능 근거는 true로 판정했습니다. 하지만 치료 설정·장비 기록을 함께 해석하는 특정 업무의 적합성은 확인되지 않았다며 false로 판정했습니다. 따라서 다음 두 범위를 분리해야 합니다.

- 모델 버전·평가지표·실험 이력을 비교하는 개발 도구 기능.
- 치료 설정과 장비 제어값의 의미·안전성을 해석하는 전문 분석 기능.

앞의 범위로 업무를 제한하면 검토할 여지가 있으나, 현재 기록만으로 치료 제어 분석까지 공급 가능하다고 승인할 수는 없습니다. F011·F044 등 미검토 프로필 통과 후보도 제한 예산 안에서 검토하되, 검토 범위를 치료 분석으로 넓혀 추천을 강제하지 않아야 합니다.

N072에서는 튜링테크의 원천이 **대조군 경과 예측·표본수/기간 검토·중간 분석·환자 예후 시뮬레이션**을 설명합니다. 수요 업무는 연구계획·자료를 대조해 **누락·불일치를 찾는 문서/자료 검토**까지 포함합니다. 첫 audit는 미지원 문서 점검 주장을 지적했고, 재작성은 대조군 예측 중심으로 바뀌었습니다. 두 번째 audit는 이 치료 영역에 대한 적용 적합성을 문제 삼았습니다.

이는 ‘같은 문장의 검증 결과가 무작위로 바뀌었다’는 증거가 아닙니다. **재작성 중 기능 범위가 이동한 것**도 원인입니다. 업무를 문서 일관성 점검과 임상 통계·대조군 분석으로 나누고, 공급기능의 지원 범위와 필요한 전문 검증을 각각 연결해야 합니다.

### 62번 뉴띵 — 기능 근거가 있는 후보도 적용조건 미확인으로 일괄 탈락

최종 audit에서 4개 후보 모두 `supplier_supported=true`, `demand_fit=false`였습니다. 그러나 네 사례를 같은 이유로 취급해서는 안 됩니다.

| 후보 | 확인된 기능 | 수요와의 간극 | 판정 설계 방향 |

유맥의 발주 기능과 PLYN의 구매·소싱 기능은 원천에 명시돼 있습니다. 그럼에도 특정 품목/업종의 경험 또는 연결 조건이 확인되지 않았다는 이유가 최종 탈락으로 이어졌습니다. **범용 기능의 적용조건 미확인을 곧바로 부적합으로 처리하는 과잉 기각 의심 사례**입니다. 실제 구매기업 데이터·제약조건을 대조하는 검토가 필요하며, 현재 분석만으로 두 업체의 도입 적합성이 확정됐다는 뜻은 아닙니다.

근본 해결은 하나의 `demand_fit` boolean을 다음 차원으로 나누는 것입니다.

1. 원천에 필요한 기능이 있는가?
2. 입력·출력과 필수 제약을 충족하는가?
3. 업종 특성이 기능의 본질적 제한인가, 추가 검증할 적용조건인가?
4. 표준 기능, 설정/연동, 추가개발 중 어느 범위인가?
5. 확인되지 않은 사항을 상담 조건으로 명시해도 되는가, 추천을 보류해야 하는가?

이 구분으로 `지원`, `조건부 검토`, `일부 지원`, `근거 부족`, `미지원`을 관리합니다. 전문 의료·생물학의 필수 기능을 조건부라는 문구로 대체하지 않습니다. 최종 추천과 사용자가 정한 03 정상 판정에는 확인된 지원 범위가 있어야 합니다.

### 생성 생략과 후보 보충에도 남은 문제

코드는 모델이 카드를 아예 생략하면 생략 이유를 기록하지 않고, 해당 쌍은 문장 수리 대상에도 넣지 않습니다. 또한 `demand_fit=false`이면 수리하지 않습니다. 이는 진짜 부적합을 반복 추천하지 않는 장점이 있지만, 적용조건만 미확인인 경우나 잘못 넓어진 업무 때문에 false가 된 경우까지 종료시킵니다.

배열에서 조용히 생략하는 방식 대신 **모든 후보 쌍에 명시적 판정·사유·문제 기능·출처 구간을 반환**하게 해야 합니다. 후보 보충은 고정 최대 6개와 회사명 순서에만 의존하지 말고, 기능 적합성 순위와 비용 한도 안의 순차 탐색으로 바꿉니다. 업무 자체가 과도하면 02의 범위를 수리한 뒤 다시 연결해야 합니다.

## 3. 0203불량 3건: 서로 다른 두 경로

### 15번 스마트키오스크/프레시스토어 — 유효 업무를 문장 오류 때문에 잃음

검증된 사실 6개, 수행기능 3개, 유효 N030 후보 1개가 있었습니다. audit는 무인 신선식품 판매·앱 예약·실시간 상품 수량이 업무 근거를 제공하며, 수요·재고·발주 계획이 Task 범위에 맞는다고 설명했습니다. 탈락 지적은 ‘정보를 검토·참고할 수 있다’는 기대효과가 구체적인 과정 변화·성과 관측과 연결되지 않았다는 것입니다.

현재 AX 분석은 audit에서 하나라도 false이면 그 후보를 삭제하고 끝냅니다. **공급기업 설명에는 1회 문장 수리가 추가됐지만 AX 업무 설명에는 대응 절차가 없습니다.** 유효 후보가 1개뿐이면 문장 하나의 문제로 02가 0개가 되고, 업무가 없어 03도 실행할 연결 대상이 사라집니다.

근본 해결은 사실·과업 적합성이 확인된 부분을 보존하고, 문제인 mechanism/process_change/expected_effects만 제한 횟수로 수정·재검증하는 것입니다. 예를 들어 데이터 보유를 전제하지 않으면서 ‘어떤 발주 검토 자료를 만들고, 담당자가 무엇을 결정하는가’를 연결해야 합니다. 측정할 KPI와 실제 달성한 개선 수치를 구분하고, 개선율을 만들어 넣지 않아야 합니다.

### 55번 모드하우스 — 담당자 검토와 팬의 발견 효과가 연결되지 않음

추천 후 담당자의 승인·공개 흐름을 조건부 제안으로 구체화하거나, 기대효과를 실제 제안한 운영자 검토 범위로 좁혀 수리할 수 있습니다. ‘전송·공개 자동화’ 기능이나 기존 운영 절차를 새로 주장할 필요는 없습니다. 출처의 `promises`·`plans`와 현재 수행 사실도 구분해, 계획을 이미 운영 중인 시스템처럼 해석하지 않아야 합니다.

### DNS 2건 — 오류 문구를 고치는 것과 주소를 복구하는 것은 다름

22:05~22:08 KST에 추가 확인했습니다. 로컬 실행환경은 네 주소 모두 이름 해석에 실패했고, 공개 DNS 조회에서도 다음 결과를 얻었습니다.

- `darlcha.com`, `snackfor.com`: A·AAAA 조회는 NOERROR이지만 주소 응답은 없음. 도메인 영역의 존재와 웹 서버 주소 레코드의 존재는 다릅니다.
- `www.darlcha.com`, `www.snackfor.com`: NXDOMAIN.

이는 조회 당시 로컬 환경에만 국한된 오류라는 설명보다 주소 레코드 부재와 부합합니다. 그러나 사이트 영구 폐쇄나 회사 소멸을 의미하지는 않습니다. **이 두 건은 OSS의 프롬프트나 모델로 복구할 수 없습니다.** 권한 있는 DNS 관리자가 레코드를 복구하거나 현재 공식 홈페이지를 확인해 입력을 교정해야 합니다. 앱에서는 NXDOMAIN·주소 없음·일시 DNS 장애를 나누고, 재시도 가능한 경우만 제한 재시도해야 합니다.

추가 DNS 결과는 당시 최종 테스트의 DNS 응답 전체를 복원한 것이 아니라 현재의 보강 증거입니다. 원래 실행 당시 확정 사실은 `gaierror`로 수집 전에 중단됐다는 것입니다.

### 대표주소 이동 3건 — www 별칭 수정만으로는 대표 도메인 변경을 처리하지 못함

현재 수집기는 `www` 유무만 동일 사이트로 취급합니다. 기업/제품 브랜드의 별도 도메인, `.kr → .com`, JS 대표주소 변경은 모두 다른 호스트가 됩니다. 기존 수정은 이동의 오류 분류를 정확하게 만들었지만 이런 관계를 확인·관리하는 기능까지 추가한 것은 아닙니다.

대표주소 확인 과정을 본문 수집 앞에 두고, 입력 주소·이동 대상·기업 동일성 근거·관계 확인일을 관리해야 합니다. 이동 단계마다 공개 IP·허용 스킴/포트·순환·횟수 검사를 유지하고 목적지 정책을 확인합니다. HTTP·meta·JS 이동이 같은 계약을 사용해야 합니다.

리다이렉트가 있다는 사실만으로 목적지가 같은 회사라고 확정할 수는 없습니다. 이번 추가 웹 확인에서도 세 목적지의 본문/소유 관계를 충분히 검증하지 못했으므로, **아직 검증 완료된 별칭 목록이라고 제시하지 않습니다.** 주소 관계가 확인돼도 목적지 접근 제한이나 자료 부족이 남을 수 있습니다.

robots 이동은 별도로 다뤄야 합니다. [RFC 9309 §2.3.1.2](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.2)는 다른 호스트를 포함한 정책 파일 이동을 설명하며, 도달한 정책을 원래 authority의 맥락에 적용하도록 규정합니다. 회사 본문을 무제한 다른 호스트로 수집하는 것과 같은 문제가 아닙니다.

### robots 2건 — 403과 521을 같은 임시 오류로 묶지 않음

403은 정책 파일 조회의 4xx 응답이며, `robots.txt` 안의 명시적 Disallow와 같지 않습니다. 521은 서버 측 5xx 응답입니다. [RFC 9309 §2.3.1.3–4](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.3)는 4xx인 unavailable과 서버·네트워크 오류인 unreachable을 다르게 다룹니다. 4xx에는 다른 자원 접근을 허용할 수 있으나, 5xx 미확정 정책에는 차단을 가정하도록 합니다.

현재 코드는 404만 예외로 허용하고 다른 오류는 중단합니다. 더 보수적인 제품 정책이지만, 그 선택을 표준의 필수 차단과 혼동해서는 안 됩니다. 개선은 상태별 정책·이유를 명시하고, 실제 인증·접근제한이나 명시 금지는 계속 준수하며, 허용 가능한 공개 자료 경로·유효 정책 캐시·재시도를 분리하는 것입니다. 403을 받았다는 이유만으로 모든 접근 제한을 우회하거나, 521을 무시하고 수집을 진행하는 방안은 아닙니다.

외부 서버가 복구되지 않으면 공식 소개자료·사용자가 제공한 자료 등 다른 출처가 필요합니다. 같은 URL에 모델 호출을 반복하는 것으로 해결되지 않습니다.

### 댄블 — 관련 콘텐츠 API 차단과 차단 요청의 제어 누락

최종 진단에서 허용 경로의 요청 카운터는 58회, 차단 이벤트는 **2,596회**, 고유 URL/종류는 63개였습니다. 차단 중 이미지는 2,549회이며 `logo-loading.png` 1,263회, `/_next/image` 1,260회가 기록됐습니다. `production-api.danble.co.kr`의 배너·피드 등 XHR도 차단됐습니다.

현재 구조는 다음 두 점에서 취약합니다.

1. 페이지 호스트와 기업의 콘텐츠 API 호스트를 같은 것으로 가정합니다. `danble.co.kr`과 `production-api.danble.co.kr`은 현재 비교에서 다른 호스트입니다.
2. 요청 수·시간 검사 전에 차단 분기에서 반환합니다. 따라서 차단 요청은 ‘최대 60회’ 카운터 밖에 있고, 같은 URL의 오류 재요청과 로그 누적에 별도 한도가 없습니다. 이는 차단 요청이 외부 서버로 전송됐다는 뜻이 아니라 브라우저 내부의 요청·차단 반복입니다.

공식 프런트가 사용하는 필수 콘텐츠 API·리소스를 확인한 후 **정확한 호스트/경로·읽기 메서드·정책·공개 IP·예산**으로 제한 허용해야 합니다. 광고·분석·개인화 인증 요청을 함께 허용할 필요는 없습니다. 모든 요청을 차단 여부와 무관하게 계수하고, URL별 재요청 한도·차단 사유 집계·중복 로그 제한을 둬야 합니다. 준비 판정도 글자 수만이 아니라 실제 기업/상품 본문을 기준으로 해야 합니다.

API 차단이 콘텐츠 미완성에 기여했다는 강한 정황은 있지만, **필수 API만 허용한 격리 재현은 아직 하지 않았습니다.** 이미지·폰트 차단만을 본문 실패 원인으로 확정하지 않으며, 25초를 늘리기만 하면 해결된다고 보장하지도 않습니다. 허용 정책을 한 항목씩 바꾼 재현에서 본문 생성과 요청 반복이 실제로 달라지는지 확인해야 합니다.
