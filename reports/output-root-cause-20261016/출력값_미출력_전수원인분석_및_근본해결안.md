## 7. 근본 해결 설계와 실행 순서

### 1순위 A. 수집 결과를 ‘페이지 수’ 대신 ‘사업 근거 품질’로 평가

1. heading과 div 본문을 DOM 순서로 함께 추출하고, 중복만 제거합니다. 특정 태그가 존재한다는 이유로 다른 본문을 버리지 않습니다.
2. 제목·메뉴·Loading·TO TOP·연락처만 있는 페이지는 본문 미확보로 판정합니다. 텍스트 길이 하나보다 사업 관련 문장·본문 비율·중복 해시·페이지별 신규 사실을 함께 봅니다.
3. 품질이 낮고 동적 표시가 있는 페이지는 선택적으로 렌더링합니다. body null을 기다리고, meta/JS 이동과 SPA 본문 준비를 구분합니다. 로딩 문구 옆에 메뉴가 붙어도 준비 완료로 보지 않습니다.
4. 외부 리소스 정책을 무작정 넓히지 않습니다. 필요한 공식 CDN/API가 확인되면 목적지 공개 IP·robots·읽기 요청·리소스 한도를 검증하는 별도 허용 설정으로 다룹니다.
5. 회사소개·사업·제품을 우선하고, 로그인·약관·게시판 댓글·동일 제품 쿼리 변형이 페이지 예산을 소모하지 않게 합니다. selvatico의 11페이지 중 다수가 리뷰·문의·로그인, 찰라는 약관·중복 제품 경로까지 포함됐습니다.
6. 페이지 오류를 분리해 내부 근거를 유지하고, 홈페이지 대표주소 문제와 하위 외부 기사 링크 문제를 다르게 처리합니다. DNS·정책 조회·렌더링·주소이동의 오류 코드도 분리합니다.

검증 기준: 최소 파서 재현에서 heading과 실제 본문이 모두 남아야 합니다. BNSR의 로딩 화면은 수집 성공으로 인정하지 않아야 합니다. biovit 이동 중 null body는 기다리고, os2019는 사용자 입력 오류로 반환하지 않아야 합니다. 외부 링크 한 개로 이미 확보한 자료가 폐기되지 않아야 합니다. 주소 차단·robots·429·공개 IP 검사는 유지합니다.

### 1순위 B. 기업 요약과 업무 기능의 합격 조건을 분리

1. 기업 소개는 검증된 핵심사업·제품/서비스 사실만으로도 짧게 표시할 수 있어야 합니다. 모든 소개에 가치사슬·3~4문장을 요구하지 않습니다. 근거가 적으면 분량을 줄이고 확인하지 못한 활동을 덧붙이지 않습니다.
2. 실제 수행 기능은 항목별 `supported/unknown`으로 판단합니다. 회사 전체의 insufficient 문자열이 확인된 개별 기능까지 차단하지 않게 합니다. 제품 존재만으로 직접 제조·기획 기능을 추정하지 않습니다.
3. audit가 문제 삼은 주장과 원래 구조 항목을 연결합니다. 문제 항목은 삭제·약화·재검토하고, 통과한 사실과 문장은 유지합니다. 잘못된 구조를 고정한 채 문장만 반복 생성하지 않습니다.
4. 생성·형식·근거 검증 실패를 구분해 문제가 있는 문장만 제한 횟수로 수정합니다. 직접 인용 사실의 원문·시제·주체도 확인해 타사 사례·의학 정보 콘텐츠가 회사 수행활동으로 승격되지 않게 합니다.

검증 기준: supermakers·mod-haus의 확인된 기업 소개는 가치사슬이 없다는 이유만으로 삭제되지 않아야 합니다. selvatico의 제품 소개와 미확인 수행 기능은 구분해야 합니다. 록야 등 네 사례에서 지적된 문장을 제거해도 확인된 핵심사업 설명이 남아야 합니다. 수정 후 실제 문장과 출처를 다시 검증해야 하며, 현 자료만으로 10건 모두 복구된다고 보장하지 않습니다.

### 1순위 C. 공급기업 적합성을 먼저 판단하고, 설명 오류를 업체 탈락과 분리

2. 솔루션명은 모델이 새로 이름 짓지 않도록 원천에서 추출한 명칭 ID/원문 구간을 선택하게 합니다. 고유 명칭이 없는 등록 서비스는 고유명과 일반 서비스 설명을 별도 필드로 보관하는 계약을 정하고, 출처에 없는 이름을 공식 제품명처럼 만들지 않습니다.
3. 공급기업의 실제 기능 적합성이 통과했으나 문장에 unsupported claim이 있으면 문제 문장만 다시 씁니다. 적합성이 없는 업체와 단순 작성 오류를 같은 ‘업체 삭제’로 처리하지 않습니다.
