# 전체 DB 공급기업 확대 및 업무당 최대 2곳 추천 계획

작성일: 2026-10-17 · 직전 조사 기준: DB 1,428곳 / 현재 추천 허용 112곳 / 범위 밖 1,316곳

## 1. 적용할 원칙

**전체 1,428곳을 검색 후보로 삼고, 기존 112곳과 같은 품질 검증을 통과한 업체 중 업무별 최대 2곳을 출력한다.**

‘전체 DB 검색 대상 편입’, ‘해당 업무에 적합한 후보’, ‘최종 추천’은 서로 다른 단계다. DB 등록만으로 추천 자격을 부여하지 않는다. 적합한 업체가 한 곳이면 한 곳을 출력하고, 검증을 통과한 업체가 없으면 사유를 기록한다. 두 자리를 채우려고 근거가 부족한 업체를 넣지 않는다.

추천 업무가 3개인 경우 최대 추천 카드 수는 6개다. 동일 업체도 서로 다른 업무에 실제로 적합하면 각각 추천할 수 있다. 한 업무 안에서는 같은 업체의 여러 제품이 두 자리를 차지하지 않도록 업체 단위로 묶는다.

이 문서는 구현 계획이다. 이번 단계에서 운영 코드나 DB를 수정하지 않았다.

## 2. DB에서 전체 공급기업을 불러오는 방법

### 전체 원문을 가진 공급기업 카탈로그 구성

1. `pool_entries`에서 AI바우처·2026년 등록 자료를 전체 조회하고 `suppliers`와 공급기업 DB ID로 연결한다.
2. 1,000건 단위의 API 반환 한도를 고려해 마지막 페이지까지 읽는다. 등록번호·공급기업 ID로 안정적으로 정렬하고 조회 건수와 중복을 확인한다.
3. 회사명, DB ID, 등록번호, 솔루션 원문, 전문분야, 홈페이지, 주소, 전화번호, 대표자명, 자료 기준연도·출처·해시를 서버 카탈로그에 구성한다.
4. 기존 F/I 형태 워크북 ID는 해당 DB 공급기업의 별칭으로 연결한다. 기존 112곳의 Task 연결과 근거도 이 관계를 통해 사용한다.
5. 워크북에 없는 신규 업체도 DB 등록 자료와 기업 식별정보가 확인되면 검색 대상에 들어온다. 이름만 같은 업체의 자료를 합치거나 다른 업체의 정보를 보충하지 않는다.

현재 코드는 `detailed_capabilities`에 있는 ID만 프로필을 조회하고, 이후 결과 구성에서도 `kb.suppliers`에 존재하는 ID를 전제로 한다. 따라서 **조회 범위와 결과 구성의 기준을 함께 DB 카탈로그로 바꿔야 한다.** 조회 목록만 늘리면 워크북에 없는 업체가 다시 제외되거나 ID 조회 오류가 생긴다.

### 기존 112곳의 근거 보존

기존 워크북 ID ↔ DB ID 연결이 확인된 업체의 Task 연결, 원문 대조 결과, 이전 검증 기록을 보존한다. 최종 추천 자료는 현재 연도의 실제 DB 원문과 등록 정보에서 가져온다. 워크북의 Task 연결은 후보를 찾는 보조 근거로 사용한다.

1,428이라는 수는 조사 시점의 건수다. 운영에서는 전체 페이지 조회 결과를 기준으로 업체의 추가·변경을 반영한다.

## 3. 새로 편입할 업체도 같은 품질의 근거를 갖추는 방법

회사별 긴 설명을 **솔루션 단위**로 나누고 다음 항목을 원문 근거와 연결한다.

| 항목 | 처리 원칙 |
|---|---|
| 솔루션명 | 원문에 실제 등장하는 명칭 사용 |
| 지원 기능 | 원문이 직접 설명하는 기능만 추출 |
| 입력·산출물 | 확인된 항목만 기록하고, 불명확하면 미확인으로 유지 |
| 적용 영역·제한 | 양식/작물, 의료/산업, 특정 공정 전용 등 실제 제한을 구별 |
| 원문 근거 | 등록번호, 원문 구간 ID, 위치·내용·해시를 연결 |
| AX Task 연결 | 검색용 후보 분류로 관리하고 실제 적합성은 별도 검증 |

예를 들어 같은 업체의 HealthTwin 설명을 AquaTwin의 기능 근거로 섞지 않는다. 원문에서 확인되지 않는 기능은 요약 과정에서도 추가하지 않는다. 기존 112곳과 신규 1,316곳에 같은 항목·검사 기준을 적용한다.

전체 원문과 검색용 인덱스는 서버에서 캐시한다. 시작 시 전체를 읽고 주기적으로 완성된 카탈로그를 교체한다. 일부 페이지만 조회된 결과가 전체 풀을 대체하지 않도록 한다. 캐시의 조회 시각·원문 버전·갱신 실패 여부는 진단에 남긴다. 브라우저에는 이번 업무에서 선정한 업체의 표시 정보만 전달한다.

## 4. 전체 DB에서 실제로 맞는 업체를 찾는 방법

업무를 생성한 뒤에는 그 업무의 메커니즘·입력·산출물을 고정한다. 공급기업 검색 과정에서 업무를 다른 것으로 바꾸지 않는다.

다음 세 경로의 후보를 합친다.

1. **기존 Task 연결 검색:** 기존에 상세 분류한 업체와 과업 연결을 활용한다.
2. **기능·산출물 검색:** 전체 DB의 솔루션 원문에서 요구 기능과 직접 산출물을 검색한다.
3. **업종·데이터 검색:** 양식장·어류·수조 센서, 공정 조건·품질 결과 등 실제 업무의 영역과 데이터 유형으로 검색한다.

각 경로에서 후보를 확보한 뒤 중복을 제거한다. 한 경로가 후보를 독식하지 않도록 검색 경로별 후보 자리를 확보한다. 기존 112곳이라는 이유나 신규 업체라는 이유로 최종 순위에 가산점을 주지 않는다.

**전체 DB로 범위를 넓히는 것만으로는 충분하지 않다.** 직전 실험에서 플렉싱크는 기존 검색식으로 전체 DB를 대상으로 해도 124위였다. 실제 양식장·센서 기능을 찾는 검색 경로가 함께 필요하다.

초기 검증 예산은 검색 후보를 최대 24곳으로 모으고, 원문·업무 사전 대조 후 최대 12곳을 정밀 검토하는 방식으로 잡는다. 적합 후보를 확보하지 못하면 질의의 동의어·적용 영역을 보완해 다음 후보를 제한적으로 검토한다. 총 검토 한도는 업무당 24곳을 초기안으로 두고 고정 사례 검증에서 조정한다. 한도에 도달해 남은 후보를 확인하지 못했다면 ‘검토 한도 도달’로 기록한다. 전체 DB에 업체가 없다고 결론 내리지 않는다.

## 5. 기존과 같은 추천 품질을 보장할 검증

아래 기준을 기존 업체와 신규 업체에 동일하게 적용한다.

| 검사 | 통과 조건 |
|---|---|
| 기업 식별·출처 | DB 공급기업 ID·등록번호·회사 정보·해당 연도 원문이 올바르게 연결됨 |
| 표시 정보 | 전문분야·설명 원문·주소·전화·대표자 및 화면 필수 홈페이지 정보가 유효함. 누락·대체 문구로 정상 처리하지 않음 |
| 실제 기능 | 제안한 솔루션과 핵심 기능이 정확한 원문 구간에 존재함 |
| 업무 적합성 | 원래 업무의 입력→기능→산출물 흐름에 직접 기여함 |
| 적용 영역 | 작물 전용을 어류용으로, 다른 종류의 임상 기능을 문서 검토로 확대하지 않음 |
| 설명 품질 | ‘왜 이 업체인가 / 어떻게 사용하나 / 업무가 어떻게 달라지나 / 상담 시 무엇을 확인하나’가 해당 회사·해당 업무에 맞게 작성됨 |
| 범위·조건 | 일부 지원, 데이터 연동, 설정·적용 경험 미확인 사항을 공개함 |
| 정직성·최종 판단 | 도입 실적·효과 수치·전문성을 만들지 않고 담당자의 최종 판단을 유지함 |

추천 문구를 작성한 뒤 독립 감사를 통과해야 최종 후보가 된다. 단어가 비슷하거나 검색 점수가 높다는 이유만으로 추천하지 않는다.

일부 단계 지원은 기존 원칙대로 허용한다. 원래 업무의 구체적인 산출물 일부를 직접 지원해야 하며 화면·PDF에 지원 범위와 미확인 기능을 표시한다. 다른 업무로 바꾸는 제안은 제외한다.

### 카드가 잘못 작성된 경우의 제한적 교정

같은 업체 원문에 직접 기능이 있는데 잘못된 제품·원문 구간·지원 산출물을 선택한 경우에는, **원래 업무에 이미 있는 산출물 안에서 한 번만 교정하고 다시 독립 감사한다.** 실제 기능 부족이나 적용 영역 충돌은 계속 제외한다.

타이드풀의 나모웹비즈처럼 ‘환경 추세 요약’ 카드는 근거가 부족해도 ‘관리 방향 검토’ 단계는 원문으로 뒷받침될 수 있다. 카드 하나의 실패를 곧바로 업체 전체의 부적합으로 끝내지 않도록 한다.

## 6. 검증 통과 업체 중 최대 2곳 선정

검토 대상으로 정한 후보들을 감사한 뒤 업체별로 묶고 다음 순서로 비교한다.

1. 원래 요구 기능·산출물을 얼마나 직접적으로 지원하는가.
2. 해당 업무의 입력 데이터와 적용 영역에 얼마나 맞는가.
3. 원문 근거가 얼마나 구체적이고 명확한가.
4. 실제 확인이 필요한 조건과 지원 범위는 무엇인가.
5. 품질이 비슷하면 두 업체가 서로 유용한 선택지를 제공하는가.

같은 조건이면 안정적인 DB 식별자로 순서를 고정한다. 검증 실패 업체는 순위 계산 대상에서 제외한다. 상세 원문이 길거나 유명한 업체라는 이유로 우선하지 않는다.

**최종 2곳은 감사를 통과한 업체에서 선정한다.** 현재처럼 먼저 통과한 업체가 한 곳 생겼다는 이유만으로 검토를 끝내면 뒤에 있는 더 적합한 업체를 놓칠 수 있다. 검토 대상으로 확정한 후보들의 결과를 비교한 뒤 최종 선정한다.

| 검증 통과 수 | 출력 |
|---:|---|
| 0곳 | 추천 공백과 단계별 원인 기록 |
| 1곳 | 1곳 출력 |
| 2곳 이상 | 적합성이 높은 서로 다른 업체 최대 2곳 출력 |

## 7. 업무당 최대 2곳을 서버·화면·PDF에 일관되게 적용

서버의 단일 정책값 `MAX_SUPPLIERS_PER_WORK = 2`를 기준으로 API 계약과 화면을 맞춘다.

| 변경 영역 | 반영할 내용 |
|---|---|
| `supplier_profile.py` | 전체 DB 카탈로그·프로필 조회, 연도·출처·기업 연결 검증 |
| `presentation.py` | DB 카탈로그 기반 후보 생성. 워크북 ID 존재 전제 해제 |
| `source_retrieval.py` | 솔루션 단위 기능·적용 영역 검색과 경로별 후보 합치기 |
| `supplier_advice.py` | 동일 품질 감사, 제한적 범위 교정, 통과 후보 비교 후 최종 2곳 선정 |
| `web_server.py` | 카탈로그·선정 결과 연결, API의 업무별 최대 2곳 계약 확인 |
| `empty_output.py` | 0곳·필수 필드 누락 검사와 2곳 초과 오류 검사 |
| `web/app.js` | 업무별 최대 2곳 표시, 같은 목록으로 보고서 요청 생성 |
| `pdf_report.py` | 업무별 최대 2곳 검증. 3곳 이상인 요청은 오류로 처리 |

내부 후보 검토 묶음 크기와 최종 출력 수를 구별한다. 소스의 모든 숫자 3을 일괄 변경하지 않는다. 업무당 2곳 제한은 최종 추천·표시·PDF 항목에 적용하고, 내부 검토 후보 수는 품질 검증에 필요한 별도 한도로 관리한다.

## 8. 같은 품질인지 확인하는 통과 기준

### 업무를 고정한 비교 검증

- 기존 112곳의 정상 추천 사례에서 업무와 원문을 고정하고 새 경로를 실행한다. DB ID 전환·범위 확대 때문에 적합 후보가 검색에서 사라지는 회귀가 없어야 한다.
- 최종 2곳 제한으로 순위 밖 업체가 제외되는 경우와, 기능상 맞는 업체를 찾지 못하는 경우를 구별한다. 기존 추천 업체명이 모두 그대로 남는 것을 품질 기준으로 삼지 않는다.
- 기존·신규 업체를 같은 평가표로 검토한다. 표본 비교 시에는 기존 112곳 출신인지 여부를 가리고 원문 근거와 업무 적합성으로 판정한다.
- 고정된 부적합 사례에서 작물용 기능의 어류 적용, 예후 예측의 임상 문서 점검 대체, 불량 예측의 원인 분석 확대 등 근거 없는 추천이 발생하지 않아야 한다.

### 실제 화면·PDF 검증

구현 완료 후 62개 URL을 실제 OSS 검색창에서 순차 점검한다. 기존 요청대로 23번 ready-cure부터 시작하고 나머지 URL까지 모두 확인한다. 표시된 업무를 하나씩 선택해 업체 수와 필수 필드를 확인하고 실제 PDF를 다운로드한다.

API·화면·PDF의 업무별 업체 ID·업체 수·추천 설명·일부 지원 안내가 일치해야 한다. 분석에 성공한 모든 업무에서 필수 필드가 출력되고 업체 수가 1~2곳이면 해당 출력 기준을 충족한다. 빈 업무는 비정상으로 분류하고, DNS·서버 수집 실패는 추천 품질 문제와 별도로 기록한다. 기존 보고서는 보존하고 새 결과를 별도 폴더에 저장한다.

최종 확인 지표는 전체 DB 수·카탈로그 편입 수·유효 프로필 수·후보 누락 원인·검증 통과율·부적합 추천·기존 사례 회귀·업무별 출력 수·응답시간이다. 정상 보고서 수만으로 품질을 판단하지 않는다.

## 9. 권장 실행 순서

1. 전체 DB 읽기·기업 식별·기존 ID 연결을 구현하고 1,428곳의 검색 편입 여부를 대조한다.
2. 솔루션별 원문 인덱스와 세 검색 경로를 연결한다.
3. 기존과 동일한 감사 및 제한적 카드 교정을 적용하고 최종 2곳 선정을 구현한다.
4. 서버·API·화면·PDF의 최대 2곳 정책을 통합 검증한다.
5. 업무 고정 비교와 부적합 사례 검증을 통과한 뒤 62개 URL을 실제 검색·다운로드한다.
