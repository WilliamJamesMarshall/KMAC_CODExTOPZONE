# 빈 출력 진단 기록

## 목적과 위치

01.기업 이해, 02.AI로 개선할 수 있는 업무, 03.추천 공급기업 중 빈 항목이 발생하면 이후 원인 조사와 구조 개선에 사용할 근거를 남긴다. 전체 검색 기록을 복원하는 기능은 아니다.

- 위치: `reports/empty-output/`
- 목록: `index.jsonl`의 각 줄이 한 검색에서 발견된 누락 사례다. 같은 검색의 여러 빈 필드는 한 사례로 묶인다.
- 상세: 목록의 `detail_file`이 가리키는 `case-날짜-시각-식별자.json`.
- 정상 결과는 저장하지 않는다. 검색 시간의 전체 누적 통계는 기존 `reports/search-timing/`에서 별도로 관리한다.
- 개발용 서버 재시작 시 파일은 유지되며, Git 및 웹 공개 경로에는 포함하지 않는다.

## 감지 기준

| 영역 | 기록하는 조건 |
| --- | --- |
| 01.기업 이해 | 실제 표시할 기업 설명이 없거나 공백뿐인 경우 |
| 02.AI로 개선할 수 있는 업무 | 업무가 하나도 없거나 개별 업무의 제목·도움 내용·개선 효과·도입 전 확인사항이 빈 경우 |
| 03.추천 공급기업 | 업무별 공급기업이 없거나, 매핑된 기업을 찾을 수 없거나, 기업명·홈페이지·솔루션명·추천 답변·상담 정보·상세정보가 빈 경우 |
| 분석 중단 | 유효한 분석 요청이 처리 도중 실패해 결과를 완성하지 못한 경우 |

`null`, 빈 문자열, 공백뿐인 값, 빈 배열을 누락으로 본다. 화면이 일반 안내 문구로 대체하는 경우에도 원래 데이터가 없으면 기록한다. 반면 업무 선택 전 공급기업 영역이 ‘업무를 선택해 주세요’ 상태인 것은 정상이며, 이미 반환된 업무별 공급기업 데이터를 기준으로 검사한다. 화면에 표시하지 않는 내부의 `activity` 필드만 비었다는 이유로는 사례를 만들지 않는다.

## 저장하는 근거

- 검색 시작·기록 시각(한국시간), 처리 시간, 입력 URL, HTTP 상태, 코드 버전.
- 입력 URL의 쿼리와 fragment, 계정 정보는 제거한다. 기존에 쌓인 파일은 변경하지 않는다.
- `pipeline.error_code`: 수집 실패는 `redirect_blocked`, `redirect_loop`, `robots_disallowed`, `robots_unavailable`, `rate_limited`, `fetch_timeout`, `crawl_delay_exceeded`, `no_content`, `fetch_failed`로 구분한다. AI 분석 오류는 `analysis_failed`, 공급기업 조회 오류는 `supplier_lookup_failed`다.
- `pipeline.crawl`: 마지막 요청의 종류(`robots`/`page`), 요청 주소, 확인된 HTTP 상태, 첫 본문의 최종 주소(`canonical_url`), 주소 이동 목록(`redirects`: 출발·도착 주소, HTTP 상태, 요청 종류). 기록하는 주소에서는 쿼리·fragment·계정 정보를 제거한다. 차단된 이동도 목록에 남는다.
- 자바스크립트 본문 수집은 `pipeline.crawl.rendering`에 페이지 주소, 처리 시간, 가로챈 요청 수를 남긴다. 동적 리소스의 이동은 `render_resource` 종류로 구분한다. 런타임 없음(`render_unavailable`), 실행 후 본문 없음(`render_failed`), 시간·용량 제한(`render_limit`)도 구분한다.
- 누락된 영역과 항목 경로, 감지 사유. `no_upstream_opportunities`는 앞 단계에 업무가 없어 공급기업을 연결할 수 없었음을 뜻한다.
- `source_pages`: 분석 입력으로 선택·정리된 공개 원문, 출처와 해시. 전체 원본 HTML이 아니라 기업 이해 단계의 입력을 같은 방식으로 재구성한 내용이다.
- `business_analysis`: 추출 사실, 사업구조, 표시 내용, 근거 검증 상태와 이슈.
- `ax_analysis`: 채택된 업무, 검증에서 제외한 업무와 이슈, 후보 수 등.
- `pipeline.supplier_profiles`: 공급기업 ID별 원본 대조 상태와 필수 프로필 누락 항목. 전화번호·주소·대표자 등의 실제 값은 저장하지 않는다.
- `pipeline.matching`: 업무별 후보 기업 ID, 프로필 조건·동일 이름 중복으로 제외된 ID, 설명 검증 전 선택된 기업 ID.
- `pipeline.supplier_advice`: 설명에 제공한 솔루션 근거, 작성 초안, 형식·인용 검증 통과 카드, 독립 검증 결과, 제외된 업무·기업 조합과 사유.
- `output`: 실제 반환 데이터의 진단용 사본. 공급기업 연락처 프로필은 값 대신 항목의 존재 여부만 보관한다.

서버 API 키나 전체 환경변수, 로그인 정보, 사용자 계정은 수집하지 않는다. 추가 AI 호출·재크롤링·DB 조회 없이 기존 처리 과정에서 얻은 데이터로 기록한다. 검증에서 탈락한 초안은 확인되지 않은 제안이며, 확정된 공급기업 역량으로 사용하면 안 된다.

## 후속 조사 순서

1. 목록에서 `missing_fields`와 해당 상세 파일을 확인한다.
2. 코드 버전·모델, `pipeline.stage` 및 예외 유형으로 처리 위치를 확인한다.
3. 01이 비었으면 공개 원문, 추출 사실과 기업 설명 근거 검증을 대조한다.
4. 02가 비었으면 사업기능 근거, AX 후보·제외 사유를 대조한다.
5. 03이 비었으면 매칭 후보 → 프로필 조건 통과 → 설명 작성·검증 순서로 어디에서 후보가 없어졌는지 확인한다. `model_omitted`, `validation_rejected`, `missing_audit`, `audit_rejected`를 구분한다.
6. 저장된 원문과 데이터를 이용해 재현 테스트를 만든 뒤, 데이터 부족·코드 결함·모델 출력·정당한 보수적 제외 중 무엇인지 확인한다. 개선 후 같은 사례와 기존 정상 사례를 함께 검증한다.

진단 기록 자체가 근본 원인을 확정하는 것은 아니다. 공개 근거가 부족하거나 실제로 맞는 업체가 없는 경우도 있으므로, 빈칸을 채우기 위해 검증 기준을 자동으로 완화하지 않는다.
