# 홈페이지 검색 실패 원인과 개선 계획

조사일: 2026-10-15 (한국시간). 실제 실패 기록, 수집기 코드, 동일 환경에서의 재현 결과를 대조했다. 아래 원인 조사와 수정 계획은 최초 조사 당시 상태를 보존하며, 적용 결과는 다음에 정리한다.

## 추가 실패 수정: 록야의 자바스크립트 본문

사용자의 추가 실패 기록은 `https://www.rokya.co.kr/`의 21:13:14, 21:13:17 요청이다. 두 건 모두 최신 주소 이동 수정 버전 `d781bf70d3beb24a`에서 HTTP 502, `crawl/no_content`로 중단됐다. 사이트 HTTP 응답 자체는 200이었고, 이전의 www 이동 차단과 원인이 달랐다.

직접 확인한 초기 HTML은 1,336바이트이며, 본문은 빈 `<div id="root"></div>`다. 사이트의 자바스크립트를 실행해야 기업 정보와 내부 링크가 나타난다. 정적 HTML 파서로는 본문이 0자로 추출됐다.

수정 내용:

- 본문이 비어 있고 script가 있는 HTML에서만 브라우저 렌더링을 사용한다. 렌더링한 DOM에서 기존 방식으로 본문과 내부 링크를 추출한다.
- 일반 홈페이지 수집에는 브라우저를 실행하지 않는다. 한 분석의 동적 페이지들은 브라우저 프로세스를 재사용하며 분석 종료 시 정리한다.
- 브라우저는 별도 비영구 컨텍스트에서 동작한다. 모든 리소스는 기존 수집기의 공개 주소·동일 사이트·robots 검사를 거쳐 제공하며, 브라우저 직접 네트워크와 쓰기 요청, 외부 리소스·프레임·서비스 워커·웹소켓을 차단한다. [Playwright 요청 처리](https://playwright.dev/python/docs/api/class-route), [서비스 워커 제어](https://playwright.dev/python/docs/service-workers).
- 페이지별 실행 시간·요청 수와 리소스 용량을 제한한다. 설치 문제, 렌더링 실패, 제한 초과를 별도 오류 코드로 안내하고 진단 기록에 실행 상태·요청 수·시간을 남긴다.
- 홈페이지 수집 후 특정 동적 하위 페이지만 읽지 못하는 경우에는 이미 수집한 근거를 유지한다. 실제 robots 금지·429 등의 제한은 계속 적용한다.
- Playwright를 의존성에 추가하고 `dev.cmd`의 실행 환경 검사 및 배포 설치 안내를 갱신했다.

## 이전 수정 적용 결과: 주소 이동

- `www`가 붙거나 빠지는 주소 이동과 HTTP→HTTPS 이동을 처리했다. 수집 정책은 scheme과 호스트·포트별로 읽고, 이동 목적지의 본문을 요청하기 전에 허용 여부를 확인한다.
- 내부 링크와 최종 응답 주소에서도 같은 별칭 기준을 사용한다. 이미 방문한 최종 주소는 다시 수집하지 않는다.
- 공개 주소 검사, 임의 도메인·내부망 이동 차단, robots 금지, HTTP 429, 이동 횟수 제한을 유지했다. 별칭으로 재이동하더라도 확인된 정책 중 가장 긴 수집 대기 시간을 유지한다.
- 원인별 한국어 안내와 `error_code`, 주소 이동 경로와 최종 주소 등 진단 필드를 추가했다. 새로 기록하는 입력 URL 및 수집 진단 URL에서 쿼리·fragment·계정 정보를 제거한다.
- 최종 테스트 결과: 79개 중 77개 통과, 외부 원본 자료가 필요한 계약 검증 2개 건너뜀. 새 수집기 회귀 테스트 11개와 검색 오류 안내·진단 기록 테스트 2개를 포함한다.

실제 Chrome 화면에서 www 없는 주소로 검색하고, 업무 선택과 보고서 다운로드를 확인했다. 두 검색은 동시에 실행했으며, 아래 시간은 이번 검증의 개별 측정값이다.

두 화면 모두 브라우저 스크립트 오류와 분석 실패 안내가 없었다. PDF는 파일 형식, 텍스트 추출 및 보고서 섹션 포함을 확인했다. 실제 UI 검증 버전은 `6190f88227adf584`다. 이후 별칭의 수집 대기 시간 유지 보완과 회귀 검증을 적용했고, 최종 개발 서버 버전은 `d781bf70d3beb24a`다. 마지막 서버에서도 두 주소의 첫 페이지와 내부 페이지 수집을 다시 확인했다.

이번 수정은 검색을 수집 단계에서 중단시키던 문제를 해결했다. 전체 결과의 빈 필드는 여전히 별도 개선 대상이다.

- N.THING의 기업 설명은 독립 근거 검증에서 일부 주장에 대한 인용 부족으로 제외됐다. 화면은 기존 안내 문구를 표시했다. 추천 업무 1개의 공급기업도 비어 있었다. 기록: `reports/empty-output/case-20261015-210400-930814-67a5a7fb.json`.
- 만나씨이에이는 기업 설명과 업무 3개가 생성됐지만 공급기업이 모두 비어 있었다. 기록: `reports/empty-output/case-20261015-210315-066329-db2519eb.json`.
- 두 사례 모두 입력 원문·검증 결과·공급기업 제외 근거와 새 수집 진단이 저장됐다. 이번 수정에서 분석의 근거 검증이나 공급기업 선정 조건은 변경하지 않았다.
- 실제 검증 검색 2건은 기존 검색 시간 기록 및 누적 통계에 포함됐다. 수집기만 직접 호출한 점검과 격리된 자동 테스트는 운영 통계에 포함되지 않는다.

## 결론

확인한 최근 실패 5건은 입력 홈페이지의 `www` 주소 전환을 수집기가 차단해서 발생했다. 검색 요청은 서버에 도착했지만, `robots.txt`를 읽는 단계에서 중단되어 AI 분석으로 넘어가지 못했다.

`https://nthing.net/`과 `https://mannacea.com/`은 모두 `www`가 붙은 주소로 이동한다. 현재 코드는 호스트명이 한 글자라도 바뀌면 외부 사이트 이동으로 판단한다. 정상적인 홈페이지 주소 전환을 처리하지 못하는 수집기 제약이 직접 원인이다.

## 동일 환경 재현

운영 검색 API 대신 수집기만 직접 실행했다. AI API는 호출하지 않았으며, 검색 시간 및 빈 출력 운영 기록에 재현 요청을 추가하지 않았다. 각 주소는 최대 1페이지만 수집했다.

| 확인 대상 | 관찰 결과 |
| --- | --- |
| https://nthing.net/robots.txt | HTTP 307 → https://www.nthing.net/robots.txt |
| https://mannacea.com/robots.txt | HTTP 301 → https://www.mannacea.com/robots.txt |
| https://nthing.net/ 수집 | `Could not read robots.txt; crawling stopped` ← `Cross-host redirect blocked` |
| https://mannacea.com/ 수집 | 위와 동일한 예외로 중단 |
| https://www.nthing.net/ 수집 | 1페이지 수집 성공, 본문 2,460자 |
| https://www.mannacea.com/ 수집 | 1페이지 수집 성공, 본문 484자 |

`www` 주소를 직접 입력하면 이번에 확인한 수집 차단은 피할 수 있다. 다만 이번 재현은 첫 페이지 수집까지 확인한 것이며, 전체 페이지 수집·AI 분석·공급기업 추천 성공까지 검증한 것은 아니다.

## 코드상 발생 경로

1. `src/oss/crawler.py:62`의 `_SameHostRedirects.redirect_request()`가 이동 목적지의 공개 HTTP(S) URL 여부를 검사한다.
2. 이어서 호스트명이 최초 호스트와 다르면 `ValueError("Cross-host redirect blocked")`를 발생시킨다. `nthing.net`과 `www.nthing.net`은 이 비교에서 서로 다르다.
3. `crawl_site()`가 홈페이지보다 먼저 `/robots.txt`를 요청한다. 이 요청의 정상 주소 전환이 위 규칙에 걸린다.
4. 이 예외는 `RuntimeError("Could not read robots.txt; crawling stopped")`로 감싸진다.
5. `src/oss/web_server.py:237`의 공통 오류 처리에서 HTTP 502와 “홈페이지 분석을 완료하지 못했습니다. 주소를 확인하거나 잠시 후 다시 시도해 주세요.”를 반환한다.

현재 화면 문구는 주소 전환 차단, 사이트 접속 실패, 모델 호출 실패 등을 구분하지 않는다. 따라서 주소가 정상인데도 사용자는 주소를 잘못 입력했거나 일시적 장애가 난 것으로 받아들이게 된다. 같은 주소로 잠시 후 재시도해도 현재 규칙은 그대로 적용된다.

## 권장 수정 범위

### 1. 홈페이지 대표 주소 확정

- 실제 HTTP 응답의 이동 경로를 따라 `example.com` ↔ `www.example.com`의 정확한 별칭 관계만 허용한다. 임의의 하위 도메인이나 전혀 다른 도메인으로의 이동을 일괄 허용하지 않는다.
- 각 이동 단계에서도 공개 IP, HTTP(S), 허용 포트, URL 내 계정 정보 금지 검사를 유지한다. 이동 횟수 제한과 순환 감지를 둔다.
- 수집을 시작하기 전에 대표 호스트를 확정하고, 그 호스트의 `robots.txt`를 확인한 뒤 허용된 본문만 읽는다. robots 파일의 주소 전환과 홈페이지의 주소 전환을 모두 다뤄야 한다.
- 대표 주소를 확정한 뒤 페이지 수집·내부 링크 선별·최종 응답 주소 검사에 같은 기준을 사용한다. 리다이렉트 예외 한 줄만 완화하면 다른 호스트 비교에서 다시 누락될 수 있다.
- 실제 robots 금지, HTTP 429, 내부망 이동 차단은 유지한다.

### 2. 실패 원인별 안내

- 수집 단계의 실패를 `주소 전환 차단`, `robots 접근 금지`, `접속 실패`, `시간 초과`, `읽을 수 있는 본문 없음`처럼 구분한다.
- 사용자에게는 단계에 맞는 한국어 안내와 가능한 조치를 보여준다. 모델 호출 실패는 별도 원인으로 표시한다.
- 내부 예외 원문 전체를 화면에 노출하는 대신, 서버에서 관리하는 오류 코드로 화면 문구와 진단 기록을 연결한다.

### 3. 재발 조사에 필요한 기록 보강

- 기존 기록에 입력 주소, 확정 주소, 실패한 요청 종류(`robots`/본문), HTTP 상태, 이동 경로, 오류 코드를 남긴다.
- 현재 기록은 단계와 예외 종류까지만 있어 `ValueError`의 구체적인 이유를 재현 없이 알기 어렵다. 제한된 구조화 필드를 추가하면 다음 실패의 원인을 바로 분류할 수 있다.
- URL 내 계정 정보·쿼리의 민감한 값·인증 정보는 진단 기록에 남기지 않는다.
- 이번처럼 상위 수집 단계가 중단된 사례와, 분석은 완료했지만 01·02·03 필드가 누락된 사례를 오류 코드로 구분한다.
